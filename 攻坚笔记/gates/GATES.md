# 发布闸门：「流畅」和「看得清」（v1166 新增）

两道闸门把老师最在意的两件事——**手感流畅**、**字看得清**——变成会红的数字。
它们都是**新文件**，不改任何现有代码：

| 文件 | 管什么 | 用时（4 核机器） |
|---|---|---|
| `test_smoothness_v1166.mjs` | 首访流量、待机耗电、进出岛速度、答题手感、揭晓/结算掉帧 | 空闲 ~115 秒，并行负载下 ~130 秒 |
| `test_contrast_scan_v1166.mjs` | 11 套主题 × 10 个画面，每段字和它脚下真实背景的对比度 | 空闲 ~170 秒，并行负载下 ~190 秒 |
| `攻坚笔记/gates/contrast_baseline.json` | 对比度基线：今天已知看不清的 166 处 | — |

实测数字、证明它们会红的回退实验、风险：见同目录 `REPORT.md`。

## 一、流畅闸门 `test_smoothness_v1166.mjs`

### 环境（尽量像低端安卓微信）
- 真 Chromium，390×844，DPR 2，触屏，微信安卓 UA，Service Worker 关闭。
- **CDP 4 倍 CPU 节流 + 4G**（下行 9 Mbps、上行 1.5 Mbps、延迟 80 ms）。
- 测试自带静态服务器：**gzip**（html/js/css/json/svg）、**ETag + 304**、`cache-control: no-cache`、正确 MIME。
- 外网：Chromium 启动参数 `--host-resolver-rules=MAP * ~NOTFOUND` + `--no-proxy-server`，**DNS 直接失败**，一个包都出不去。
  **故意不用 Playwright 的 `route()`**：路由会关掉 HTTP 缓存，预载、保活就测不准了。
- 所有点击都是真手指（`touchscreen.tap`），点之前先滚到中间、确认最上层就是目标。

### 量什么、上限多少、为什么

上限 = **本分支在并行负载下的最差值 + 余量**，同时**低于任何一次回退实验的值**。
下表「本分支」是 6 次空闲 + 6 次并行负载的范围（负载 = 同时跑 3 个重浏览器测试；其中 3 次「重负载」= 同时跑对比度闸门 + 2 个重测试）；「回退」是 REPORT.md 里的回退实验（空闲机器上跑的）。

三个小游戏：**听音辨义**（8 题，2 题故意答错走小课）、**完形填空**（6 题，2 错）、**极速60秒**（10 题，2 错），
孩子是「进度多」的夹具（27 个岛、约 900 已学 / 200 错词 / 300 复习计划，和 `test_answer_cost_v1165` 同一个配方），
在首页外壳的 iframe 里玩——这是孩子真实的样子。
Event Timing 低于 16 ms 浏览器不上报，记作 16。

**掉帧**：在岛的框里跑一个 rAF 采样器，相邻两帧间隔 g，掉帧数 = Σ max(0, round(g/16.7) − 1)。
**长任务**：每个框都挂 `longtask` 观察器，按绝对时间去重后算落在窗口里的部分。

### 已知会撞车（为什么 S6 用中位数 + 棘轮）
孩子玩的时候，存档每变一次，`hansen_cloud_save_v965.js` 最多攒 8 秒就 `syncNow({force:true})`，
在主线程上把整份备份码重建一遍（`hansen_backup_v944.js` 的 `exportCode → build/collect/validate`），
4 倍慢 CPU 下 100–500 ms。它落在哪一次揭晓里是随机的，所以单看「最差一次」会抖。
`SMOOTH_PROFILE=1` 会在每次揭晓时抓 CPU 剖析，打出最费时的函数——就是这样抓到它的。

### 机器基准
开头和结尾各跑一段固定的脚本 + 排版（4 倍节流），记成 `benchStart / benchEnd`（ms）。
**只记录，不参与判定**——如果闸门在某台机器上红了，先看这两个数：空闲机器 45–100 ms，并行负载 55–128 ms。
远超这个范围说明机器本身太慢（比如 CPU 被别的进程占满），先换时间再跑一次。

## 二、对比度闸门 `test_contrast_scan_v1166.mjs`

### 量哪些
- **主题 11 套**：8 个免费配色（暗：深空蓝 cosmos、暗夜紫 violet、极光青 aurora、森野绿 woods；
  亮：云端白 cloud、樱花粉 sakura、奶油杏 cream、薄荷绿 mint）＋ 付费代表：金币·樱花粉在暗底 / 亮底（`coin_pink_dark` / `coin_pink_light`）、画廊·童话镇（`gallery_fairy`，全屏画布）。
- **画面 10 个**：首页第一屏、岛屿菜单（美食岛）、听音辨义出题 / 答对揭晓 / 答错小课、完形填空出题 / 答对揭晓、极速60秒出题、听音结算页、设置。

### 怎么量（和主题审查 `攻坚笔记/next_inputs/theme_scripts/contrast_lib.mjs` 同一套方法）
1. 动画全部定格：有限的快进到结束，无限的取消回到开头。
2. 收集每段字：位置、颜色（含 opacity 链、`-webkit-text-fill-color`）、字号字重、是否在最上层（被盖住的不算）。
3. 用 5 个 id 权重的选择器 + 行内 `!important` 覆盖，把所有字、描边、`text-shadow` 设成透明，截一张「只有背景」的图。
4. 每段字的背景 = 方框里真实像素的**亮度中位数**（字已经藏起来，**抗锯齿边混不进来**；渐变、图片、画布都算）。
   前景 = CSS 颜色按 opacity 合成。大字（≥24px，或 ≥18.66px 且 ≥700）要 3:1，其他 4.5:1（WCAG AA）。
5. 渐变字（`background-clip:text`）量不了，跳过。带描边 / 阴影的照常按「没有描边」算（和主题脚本一致：描边帮忙，但不算进比值）。

**让它每次都一样**：
- `Math.random` 换成固定种子，每轮游戏开始前重新播种 → 每次出同一批题。
- 全屏画布主题（IMAX / 画廊）整套用「减少动态效果」：引擎只画一张静止帧，也不再吃随机数。
- 截图用自带的 PNG 解码器读（不依赖 Python / PIL）。
- 实测：同一台机器连跑两次，2872 段字里 99% 差 ≤0.01，最差 0.07。

### 判定
- **C1** 每个画面至少量到 4 段字（否则画面没出来，红）。
- **C2** 不达标的字必须已经在基线里。基线的键 = `主题|画面|元素路径`
  （元素路径 = 最近的 id + 中间两层 + 自己的 tag/class，去掉 correct/wrong/show 这类状态 class；不含文字，换词不影响）。
- **C3** 基线里的字不许比基线低 **0.25** 以上（同一段字两次量差 ≤0.07，留 3 倍多余量）。
- 已经达标的会打印 🎉「可以从基线删掉」，不算失败。

### 怎么安全地更新基线
基线是主题 2.0 要一点点消掉的清单。**只在下面两种情况更新：**
1. **修好了**（🎉 提示出现）：跑 `CONTRAST_WRITE_BASELINE=1 node test_contrast_scan_v1166.mjs`，
   然后 `git diff 攻坚笔记/gates/contrast_baseline.json`——**只应该看到删掉的条目**。看到新增或比值变低，就是把新问题洗白了，别提交。
2. **有意的新画面 / 新设计，确认过暂时做不到达标**：同样重写，diff 里新增的每一条都要在提交说明里写清楚是哪段字、为什么暂时接受。

规矩：
- 测量有一个画面没量到（C1 红）时，脚本**拒绝重写基线**——坏的一次测量不能变成基线。
- 不要手改比值来让测试通过。
- 加新主题 / 新画面：改脚本里的 `PRESETS` / 步骤，再重写基线；diff 里会看到整块新条目，逐条过一遍。
- 调试：`CONTRAST_ONLY=cosmos,cloud` 只跑部分主题；`CONTRAST_SHOTS=目录` 存截图人工复核；`CONTRAST_JSON=文件` 存全部测量。

## 三、以后要改 `分批跑测试.py` / `jarvis_gate.py` 的地方（这次没改，只写清楚）

两道闸门都能被现有的 `glob('test_*.mjs')` 自动发现，**不用登记**。但现在的超时会把它们挡在门外：

1. **超时。** `jarvis_gate.py` 普通档每个测试 45 秒（`per_timeout = 120 if deep else 45`），重测试 ×3 = 135 秒，
   复核 `per_timeout + 20`。两道闸门要 115–190 秒 → 普通档会被判「慢」写进 `.jarvis_slow.json`，**以后每次都跳过**，
   等于没有闸门。建议加一张按名字的超时表，优先于 `per_timeout`：
   ```python
   PER_TEST_TIMEOUT = {'test_smoothness_v1166.mjs': 360, 'test_contrast_scan_v1166.mjs': 420}
   timeout = PER_TEST_TIMEOUT.get(os.path.basename(t), per_timeout * 3 if heavy else per_timeout)
   ```
   复核那一段（`timeout=per_timeout + 20`）也要用同一张表。
   `分批跑测试.py` 的 `PER_TEST = 300` 对对比度闸门在负载下（~190 秒）够用，但余量小；建议同样用这张表（420 秒）。
2. **别和别的浏览器测试挤着跑流畅闸门。** 它的时间类上限已经按「同时跑 3 个重浏览器测试」标定过（并行负载下也全绿），
   但 jarvis 普通档是 4 线程。最稳的做法：把 `test_smoothness_v1166.mjs` 放进「重测试段」（2 线程），
   即在算 `_heavy` 时无条件加入它（不依赖 `.jarvis_time.json` 里有没有历史耗时）。
   对比度闸门不看时间，可以留在并行段。
3. **慢名单豁免。** `.jarvis_slow.json` 里永远不该出现这两个名字；写慢名单前过滤掉（它们超时 = 真问题，该算失败）。
4. **指纹。** 两边的 `fingerprint()` / `_fingerprint()` 只哈希 `hansen_*.js / sw_*.js / test_*.mjs / template.html / *.py` 和 HTML 大小。
   基线 `攻坚笔记/gates/contrast_baseline.json` 改了，续跑存档不会作废——旧结果会给新基线背书。
   两个文件要**一起**把 `攻坚笔记/gates/*.json` 加进哈希（两边必须完全一致，否则闸门不认存档）。
   另外 CSS 改动（`*.css`）和 index.html 内容改动也会影响这两道闸门，而 HTML 只算了大小——同样大小的改动会漏，值得一起补。
5. **环境变量。** 闸门里不要设 `SMOOTH_ONLY` / `CONTRAST_ONLY` / `SMOOTH_PROFILE` / `CONTRAST_WRITE_BASELINE`。
   可以在 jarvis 启动子进程时显式清掉这四个，防止有人本地设过忘了关。

## 四、上限什么时候该改

- **代码变快了**（比如修好云存档整份重建）：把对应上限往下收，留同样比例的余量，把实测写进提交说明。
  棘轮类（S4 被盖住的首页动画、S6 最差一次揭晓）修好后一定要收紧，否则它们会慢慢长回去。
- **有意加了东西**（比如首屏加一张图）：S1 字节数会涨。先问「孩子第一眼需要它吗」；需要的话把上限改成新实测 + 20%，
  提交说明写清楚加了什么、多少 KB。
- **闸门红了但你觉得是机器抖**：先看 `benchStart/benchEnd`，再单独（不并行）跑一次。
  单独跑还红，就是真问题——不要靠调大上限来过。
