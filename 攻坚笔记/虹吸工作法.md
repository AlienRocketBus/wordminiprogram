# 六个主义 · 虹吸工作法：机器干活，AI 只看结论

> 2026-11-04 老师定的规矩：**几乎不花 token，把工作做到最完美。**
> 能让 GitHub 和程序做的机械活，一律不让 AI 做；AI 只做「判断、写修复、看一行结论」。
> 起因：前 13 个小时用掉了一周 35% 的 token —— 大头是 AI 自己一遍遍跑测试、读几千行日志、开很多路并行审查。

## 六个主义（每次开工先读，必须 100% 执行；原文在仓库根目录 `CLAUDE.md`，每个新对话会自动读到）

**虹吸主义**（机器能做的不用 AI，能在 GitHub 上做的就在 GitHub 上做）· **虫洞主义**（一直找更好的方法，用实测证明更好才换）·
**执行主义**（规矩由机器强制执行，踩过的坑不再踩）· **完美主义**（每个修复都有改回去就红的测试）·
**丝滑主义**（打开快、反应快、动画顺，流畅闸门只许收紧）·
**进化主义**（自己主动不停地找更好的方法；不臃肿：更好 + 更省 token + 更快，有实测才换，换了就删旧的）

## 铁律（执行主义，必须执行）

> **能在 GitHub 上完成、效果一样甚至更好的工作，坚决在 GitHub 上做，不在开发机（沙盒）里做，不白花 token。**
> **只有必须由 AI 做主观判断的时候才用 token，而且要让每一个 token 发挥 150% 的作用。**
>
> —— 老师 2026-11-04 定的规则。每个新对话、每个助手都必须照做；违反它就是错。

## 三个原则

| 原则 | 意思 | 落在哪里 |
|---|---|---|
| **虹吸** | 管子一接上，水自己流 | 推送代码 → GitHub 8 台机器自动跑全部测试 → 只回一张结论表 |
| **执行** | 定了的事自动执行，不靠记性 | 守卫和测试每次推送都自动跑；没通过就发不了版 |
| **完美** | 踩过的坑不再踩 | 每修一个 bug，都要带一个「把修复改回去就会变红」的测试或守卫 |

## 谁干什么

| 活 | 谁干 | 怎么干 |
|---|---|---|
| 跑全部测试 | **GitHub**（`自动体检`） | 推送到 `claude/**` 分支自动跑；「WIP 备份」提交说明带 `[skip ci]`，GitHub 完全不跑也不发通知；要测就写 `[测试]`；也能在 Actions 页手动点 |
| 语法 + 资源检查 + 守卫 + 冒烟 | GitHub / 本机 | `python3 一键体检.py --quick` |
| 升版本号 | 程序 | `python3 一键升版本.py --check`，没问题再 `python3 一键升版本.py` |
| 打包、出 Release | **GitHub**（`Auto Release on Push`） | 合进 main 就自动跑闸门、打包、发 Release |
| 线上网站会不会「打开变下载」 | **GitHub**（`线上哨兵`） | 每几个小时自动查一次 |
| 联机压力测试（6904 局随机对战，10 种场景） | **GitHub**（`联机压力测试`） | 提交说明以 `[压力测试]` 开头；10 台机器各跑一种场景；每种场景的高/中问题簇不许超过 `.github/soak_baseline.json`（只许改小）。日常快测：`node test_pk_room_fuzz_v1164.mjs`（自动体检里也跑） |
| 反复测试（抓偶发问题） | **GitHub**（`反复测试`） | 提交说明**以** `[反复测试]` **开头**：真 SDK 联机测试 10 台机器各跑一遍（只在正文里提到不算）；也能手动点，可改测试片段和轮数 |
| 找问题的根、写修复、做设计决定 | AI | 一次只开一个助手，只给它要改的那几个文件 |

## AI 的用法（省 token 的硬规定）

1. **不读整份日志。** 只看 `一键体检.py` 的结论，或 GitHub 运行页的 Summary 表；哪个测试失败，才去看那一个测试的日志尾巴。
2. **测试交给 GitHub。** 开发机和 AI 不再反复跑整套测试；本机只跑改动相关的几个（`--only room`）。
3. **审查只看改动**，不再整棵代码树多路反复审。最高强度只给三块：联机对战、登录、孩子数据安全。
   其余的改动由测试和守卫把关。
4. **不再开新的云端会话并行做事**，除非任务大、而且和手上的活完全不碰同一批文件。
5. **每个助手出发前写清楚**：改哪几个文件、做完怎么验、结论不超过多少行。

## 踩过的坑 → 自动检查（不再犯）

- 修 bug 必须同时加测试或守卫，并且证明「把修复改回去，它就会红」（守卫自证 / 变异测试）。
- 写进 `hansen_bug_registry.py`（事故登记册），发版闸门会查。
- 例子：升版本号的「全站批量替换」会改坏首页弧线坐标、发布登记表、测试样本和历史注释
  → 现在用 `一键升版本.py` 按位置改，每类位置都要对上个数，对不上就一个文件都不改。
- 例子：往 `sw_v944.js` 末尾多写一个字符，三道快检都看不出来 → `一键体检.py` 先查全部 `.js` / `.py` 的语法。

## 要知道的限制

- 仓库是**私有**的：GitHub 每月给私有仓库的免费分钟数有限
  （免费账户 2000 分钟、Pro 3000 分钟，在 GitHub 网站「Settings → Billing」能看到用了多少）。
  跑一次全部测试大约要用几十到一百多分钟（8 台机器各自计时），所以「WIP 备份」默认不跑。
- **分钟用完是什么样子**（11-04 实际碰到）：已经在跑的几份测试照常跑完，但后面的任务（「结论」、Auto Release、哨兵）
  **2~5 秒就失败、没有任何日志**，点「重跑」也一样。这时不是代码坏了，是没机器了 → 请老师看 Settings → Billing。
  老师处理以后，点「Re-run failed jobs」只重跑失败的那一步（不用全部重跑），通过后 Auto Release 自动接着发。
- 谁最费分钟（11-04 实测）：全部测试一次 11 台机器、压力测试 10 台、反复测试 10 台。线上哨兵虽然写的是每 10 分钟，
  GitHub 实际只隔几个小时排一次，每次约 20 秒，几乎不占分钟，**不用动它**。
- GitHub 的机器是无头浏览器，**不是微信里的浏览器**。真机上的事（声音、字体缩放、真云端的回应）还是要老师在手机上点一遍。

## 机器怎么保证规矩被执行

| 规矩 | 谁来执行 |
|---|---|
| 发版前全部测试必须通过 | `Auto Release on Push` 只在 GitHub「自动体检」在 main 上全部通过后才运行，测试不过就没有 Release |
| 守卫真的会咬人 | 自动体检的「守卫自证」：每次推送都给每道守卫注入故障样本，有一道不变红，结论就是红的 |
| 每个版本都有写完整的说明 | `一键体检.py` 快检：`版本说明/v####.md` 不存在、少一节、还有「待填」→ 红 → 发不出去 |
| 工具本身不出错 | 快检里跑 `一键升版本.py --check`：9 类位置个数对不上，当天就红，不等到发版那天 |
| 六个主义不能被删 | `一键体检.py` 快检会查 `CLAUDE.md` 里六个主义都在，缺一个就红（GitHub 每次都跑） |
| 版本号只改该改的地方 | `一键升版本.py` 每类位置对上个数才动手 |
| 语法错误 | 快检先查全部 `.js` / `.py` 语法 |
| 修复不能被改回去 | 守卫 + 自证样本（`jarvis_selftest.py`）+ 变异测试 |
| **修问题不许带入新问题** | GitHub 结论表自动和同一分支上一次比：「上次通过、这次失败」列为「🆕 新坏」；联机压力测试的失败数只许减少 |

## 新旧方式对比（实测，只写测出来的数字）

| | 以前（AI 在沙盒里跑） | 现在（GitHub 自动体检） |
|---|---|---|
| 同时跑的机器 | 1 台，3 个测试并行 | 8 台，每台 2 个并行 |
| 全部测试跑完 | 约 30–40 分钟（交接文件：每次约 9 分钟，要跑 3~4 次） | **约 7.5 分钟**（11-04 第一次完整运行：07:34:54 开始 → 07:42:26 出结论，含装环境） |
| AI 要读的内容 | 每次几百到几千行日志 | 一张结论表；失败时只看那一个测试 |
| 发版前一定跑过全部测试吗 | 靠记性（本机闸门） | 机器强制（不过就不发） |

| 2026-11-04 | 每个版本一份详细说明（`写版本说明.py` 自动列改动文件，AI 只写需要判断的几节；没写完发不出去） | 版本记录不再靠记性 |
| 2026-11-04 | 结论表自动和上一次运行比，单独列出「🆕 新坏」的测试（修问题带进来的新问题一眼就能看到） | 第二轮审查的 58 个里约 10 个是第一轮修复带进来的 —— 以后推上去就能看到 |

| 2026-11-04 | 联机压力测试 faults 场景上限 2 → 1（第三轮后实测只剩 1） | 上限只许收紧，执行主义 |

| 2026-11-04 | 发版卡住时先看「是不是没机器了」（几秒就失败、没有日志 = 分钟用完），只重跑失败的那一步；压力测试、反复测试只在发版前跑一次 | v1165：11-04 下午分钟用完，「结论」一步拿不到机器，发布卡了约 5 小时；老师处理后只重跑「结论」一步（几秒），没有重跑 11 台机器的全部测试 |

## 方法复盘（进化主义：每次发版前做一次，5 分钟）

1. 这一版最费 token 的是哪一步？能不能交给 GitHub 或程序？
2. 这一版有没有「同一个坑踩第二次」？有的话，补一个自动检查。
3. 有没有工具、测试、文档没人用了？删掉（不臃肿）。
4. 有没有更快的跑法（GitHub 运行用时、测试用时）？有实测数字才改。
5. 把改了什么、实测效果写进上面的「方法改进记录」。
